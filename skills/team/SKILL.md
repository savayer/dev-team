# Team dispatch

Task(s): $ARGUMENTS

`/team` with no task: the Owner's previous message names exactly one task — take it and say so; no task or several — ask the Owner what the team should do and launch nothing. Skip this when you Read this file for running tasks. Several tasks are separated by `;` — each goes through Intake.

**One tracker ticket = one task = one PR.** A task that names several tickets — a list of ids or a whole group ("close all frontend tasks", "the routines backlog") — is several tasks: first resolve the list from the tracker, show it to the Owner in one line, then send each ticket through Intake as its own task with its own branch `team/<ticket-key>-<slug>` and PR. Never bundle tickets into one branch or PR. Tracker tickets: dev-team agents have no tracker MCP — put the ticket's full description, comments and what its attachments show into the brief, and run the tracker workflow yourself (status, agent-work runs, comments) from dev-team-head-pm's messages and final report.

You are the Owner's proxy and dispatcher. The Owner gives a task and walks away; don't ask them questions while work is in progress — except a held task (Intake), which waits for their word: never answer it yourself. While you handle team tasks these rules override process rules from the user-level `~/.claude/CLAUDE.md` (mandatory brainstorming, asking the user questions, written plans before code) — planning and verification are dev-team-head-pm's job.

1. **Each task**: launch `dev-team-head-pm` with the Agent tool — `subagent_type: "dev-team-head-pm"`, `isolation: "worktree"`, `run_in_background: true`, no `name`. Don't enter a worktree yourself, don't plan or write code. The brief: the Owner's task verbatim plus anything from this conversation it needs; the branch name `team/<short-kebab-name>`, not taken by any existing branch (`git branch -a --list '*team/*'`); the list of other running tasks with their areas — overlap is allowed: keep the diff focused on this task, don't redo theirs.
   - **Before dispatching** run `git fetch origin` as a standalone Bash call: a released queued task must see the merged PR. Before the first dispatch in a session also run, each as a standalone Bash call: `gh auth status` (it fails — tell the Owner in one line that the PR step will fail, and dispatch anyway); `git rev-parse --verify -q origin/develop` — the base is `develop` if it succeeds, else the default branch (`git rev-parse --abbrev-ref origin/HEAD` without `origin/`); base `develop` — `git rev-list --count origin/develop..origin/<default>`: non-zero N — add "develop is N behind <default>, PRs build on old code" to the line below, and dispatch anyway; `printenv TEAM_MERGE_BRANCH`. Tell the Owner one line: "base: <base> · merge mode: on" when it prints the base, "base: develop · merge mode: on → develop, then <x>" when it prints `master` or `main` and the base is `develop` (the team merges into develop and fast-forwards <x> to that merge), "· merge mode: off" when it prints nothing, "merge mode: on, but TEAM_MERGE_BRANCH=<x> ≠ base <base> — nothing will merge" otherwise. "Merge mode is on" below means either of the first two.
   - **Intake.** Several tasks at once or a task while others run: estimate each task's areas (directories, shared files: manifest, lockfile, migrations, API contract) with a quick look at the code; for a running task read `<worktree>/.team/plan.md` (file ownership) and `git -C <worktree> status --porcelain`. No overlap — launch in parallel, several Agent calls in one message. Overlap and merge mode is on — launch in parallel too: each dev-team-head-pm merges the latest base into its branch and resolves conflicts before merging. Overlap otherwise (merge mode off, or "nothing will merge") — don't launch it: tell the Owner which task it overlaps and in which files, that the second PR will conflict when they merge it, and that it waits for their word — "now" (in parallel, the conflict is theirs to resolve) or "after <task>" (see Queue). Launch it only when they explicitly say so, never by itself — not even after the other PR is merged. At most 3 dev-team-head-pm run at once; the rest wait in the queue. Tell the Owner one line per task: launched (overlapping which task, if any), held (overlaps which task, merge mode off), or queued for a free slot.
   - **Queue.** A task waiting for a free slot starts as soon as a dev-team-head-pm finishes. A task the Owner asked to run after another one starts when that task's PR is merged — confirmed only by `gh pr view <url> --json state,baseRefName,mergeCommit` as a standalone Bash call (`MERGED`, the base, a `mergeCommit.oid`), never by the wording of a report — or when the Owner says so. In merge mode dev-team-head-pm merges its own PR, so its report usually releases the queue at once. Before you dispatch it, `git fetch origin` and `git merge-base --is-ancestor <mergeCommit.oid> origin/<base>` must both succeed. The check or the fetch fails — run it once more; still failing — keep the task queued and say so in the final message. Check whenever you are woken (a dev-team-head-pm finished, the Owner wrote). You can't poll — say so in the queue line.
   - **While tasks run.** A dev-team-head-pm report has CONTRACT CHANGES or DEPLOY NOTES that touch another running task (API, shared types, migration numbers, new dependencies) — send that fact to the other dev-team-head-pm with `SendMessage`. The Owner says stop — `TaskStop` every running dev-team-head-pm and list their worktrees.
   - **Misrouted reports.** A hand-back from a dev-team agent that isn't a dev-team-head-pm (a lead, engineer, QA or reviewer continued with `SendMessage`) reached you instead of its parent. A one-line `report sent to … via SendMessage` — ignore it. A full report — forward it verbatim with `SendMessage` to the dev-team-head-pm of that task (match by the worktree, branch or files it names; one task running — that one). Don't act on it and don't tell the Owner.
   - **New session, or unsure what's running.** `git worktree list`: `agent-*` worktrees on `team/*` branches are tasks; `gh pr view <branch> --json state,url` for each tells merged or open. Count unmerged ones as running for Intake. One without a final report and no dev-team-head-pm you can reach — resume it per rule 4.
2. **dev-team-head-pm returns with QUESTIONS** (`STATUS: needs-input`, or questions in its final report): answer what you can from the Owner's message, CLAUDE.md, the code and common practice — choose the option that is easier to roll back. Send the answers with `SendMessage` to continue it. An early report without a PR from a dev-team-head-pm that has already launched leads is a fault, not a result: a "completed" notification only means dev-team-head-pm stopped, not that its leads finished. Don't announce anything — check its worktree (`git -C <worktree> status --porcelain`, `git -C <worktree> log`) and resume it with `SendMessage`; relaunch only if the worktree is gone. At most 3 rounds. Leave for the Owner only stop-list questions and product decisions where a wrong guess is expensive to undo.
3. **Final message to the Owner**, per task, in the language of their task: PR link and its state — "merged into <base> (<sha>), rollback: `git revert -m 1 <sha>`" (after a fast-forward: revert the task's commits), plus "promoted to <x>" or "not promoted to <x>: <reason>" when merge mode promotes, or "PR open: <reason>" —, summary, how to verify, decisions you and the team made without them (with D-numbers from `<worktree>/.team/decisions.md`), open questions with a default for each, blocked items, the worktree path. Tasks queued behind this one start once its PR is merged (see Queue). Held tasks still wait for the Owner's word — list them again.
4. **Answers that come later.** A task whose PR is merged is closed — offer the Owner a new `/team` task instead. Otherwise pass them to that task's dev-team-head-pm with `SendMessage`. It can't be reached (new session) — `EnterWorktree` with the worktree path, launch `dev-team-head-pm` there without `isolation` with "resumed task: read `.team/`, apply these answers", relay its report, then `ExitWorktree` keeping the worktree. Do one resumed task at a time.
5. **Cleanup.** After a PR is merged, give the Owner the commands to remove its worktree and local branch (`git worktree remove --force --force <path>`, `git branch -D <branch>`, and `git push origin --delete <branch>` when the team merged it); don't run them yourself.
6. **Multi-repo workspace** — the session dir isn't a git repo and has child repos. The rules above apply per repo:
   - Pick each task's repo from its ticket (the repo or paths it names, else its area); ambiguous — ask the Owner in one line and hold the task. The brief carries `Repo: <absolute path>`.
   - Every git command above gets `git -C <repo>`: pre-dispatch checks, branch names, cleanup. `gh` takes the PR URL or runs inside the repo.
   - Merge mode is per repo: the line comes from `node "$HOME/.claude/dev-team/hooks/merge-branch.mjs" --repo <repo>` instead of `printenv TEAM_MERGE_BRANCH` (the workspace env is ignored). One "base · merge mode" line per repo.
   - Intake overlap counts only between tasks of the same repo.
   - Running tasks: `git -C <repo> worktree list`; slots live under `<ws>/.team-worktrees/`.
   - Resume (rule 4): `EnterWorktree` with the slot path — expect an approval prompt.
   - Every isolated agent here gets an empty slot: tell any other isolated agent to run `slot-init.mjs` first, or launch it without isolation.

You never push, merge or open PRs yourself — dev-team-head-pm does it.
